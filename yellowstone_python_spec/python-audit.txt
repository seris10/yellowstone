## Overall assessment

**This is a good scientific-software scaffold, but it is not yet an advanced scientific simulation.** It is considerably better organized and more scientifically cautious than a typical game ecology script. However, most of the scientific modules currently implement **simple response curves, authored rules, or one-time adjustments to animation parameters**, rather than substantial simulations of the processes they describe.

For your goal—a Python showpiece that someone can explore inside a Godot world—the foundation is useful. But the next step should be **deepening a few connected scientific systems**, not adding more loosely connected modules.

My recommendation is to make this your central demonstration:

> **Hydrothermal discharge → river hydraulics and temperature → aquatic insects → trout and dipper behavior**, with **snowmelt and soil moisture** providing seasonal context.

That gives you an identifiable Yellowstone story, meaningful mathematics, visible consequences, and a reason for Python to be doing substantial work.

I reviewed the supplied files statically. I have not run the package, and I have not seen the research documents, configurations, data, Godot scripts, or the imported validation/provenance modules. Where a capability might exist in those missing files, I distinguish that from what these files actually demonstrate.

# 1. What is already good

There are several things worth preserving.

### Scientific honesty

The repeated distinction between *illustrative*, *authored*, *calibrated*, and *measured* is excellent. Likewise:

- Trout activity is not presented as mortality.
- Sparse grazer loops are not presented as animal abundance.
- Pool depths are not claimed to be surveyed bathymetry.
- You avoid a simplistic wolves–elk–willow causal slider.
- You distinguish siliceous sinter from travertine.
- You recognize that pool color is not simply a universal temperature rainbow.

These are important foundations for a credible project.

### A sensible production pipeline

Immutable inputs, derived builds, sidecars, checks, and a separate publishing step are all good ideas. This is much closer to scientific software practice than directly changing world data from miscellaneous scripts.

### An actual mathematical starting point

The river model is not just a temperature lookup. It has storage, upstream transport, lateral inputs, atmospheric exchange, stable substeps, and budget accounting.

The vegetation model also has a recognizable growth–consumption structure, and the snow model uses a legitimate first approximation.

### Useful boundaries between science and presentation

Keeping geography and placements stable while allowing environmental states to change is sensible. An advanced simulation does not need to randomly regenerate the landscape to demonstrate its sophistication.

**The weakness is not the overall direction. It is the gap between the modules’ descriptions and the depth of their implementations.**

# 2. The biggest architectural issue: this is primarily a build-time system

At present, Python mostly:

1. Reads a baseline.
2. Runs a short river simulation.
3. Advances some patch indices.
4. Adjusts wildlife timing parameters.
5. Runs a separate seasonal calculation.
6. Writes JSON and illustrative images.
7. Publishes them to Godot.

That can support a good visualization, but it does not yet demonstrate a continuously evolving, coupled Python simulation.

For example:

- `update_trout()` does not simulate fish choosing refuges.
- `update_wildlife()` does not continuously couple bird decisions to insect availability.
- `update_grazers()` does not simulate forage-driven movement.
- The plume texture is not generated by transport physics.
- The suitability texture is not generated by the suitability model.

**A viewer could see attractive effects without seeing much of the Python mathematics in action.**

You have two good options:

### Option A: Python generates scientific time-series replays

Python runs the substantial simulation offline, exporting timestamped fields and agent states. Godot plays those back and interpolates between them.

This is scientifically legitimate and easier to make reliable.

### Option B: Python runs a persistent simulation service

Godot sends scenario changes to Python; Python advances the model and returns updated fields and agent states.

This is more impressive interactively, but adds synchronization and deployment work.

In either case:

- Python should own scientific state.
- Godot should own rendering, player movement, and visual interpolation.
- Shared quantities should have one authoritative definition.
- Scientific time should be explicit.
- Godot should not independently evolve a second, slightly different version of the same ecosystem.

The current emphasis on “mirroring Godot exactly” is useful for initial compatibility, but **Godot’s existing approximation should not remain the ceiling on the Python science**.

# 3. File-by-file scientific assessment

## `hydro_thermal.py`

### Current level: the strongest scientific module, but still a simple compartment model

This is a serial, well-mixed reach model—essentially a chain of continuously stirred tanks.

That is a valid approximation. It is also relatively basic compared with what would make this project a scientific showpiece.

### What is good

- Flow-weighted mixing is appropriate under the stated assumptions.
- Constant-volume heat accounting is coherent.
- Upstream temperatures are taken from the previous substep, avoiding order-dependent updates.
- The timestep restriction helps maintain stability and bounded behavior for the linear model.
- Lateral sources are explicit.
- The exponential cooling helper has a recognizable physical basis.

### Important limitations

**Atmospheric exchange is represented by one relaxation timescale.**

```python
atm = (air_c - old[i]) * vol / cooling_seconds
```

This lumps together processes that behave differently:

- Shortwave radiation.
- Longwave radiation.
- Sensible heat transfer.
- Evaporative heat loss.
- Bed exchange.
- Possibly groundwater and geothermal contributions.

Water does not simply relax toward air temperature under all conditions.

**The plume is an artistic Gaussian, not a transported thermal plume.**

It does not use:

- River geometry.
- Local velocity.
- Discharge.
- Turbulent mixing.
- Channel boundaries.
- A source heat budget.

It can therefore suggest spatial scientific detail the underlying model does not possess.

**The budget checks mainly demonstrate internal accounting consistency.**

That is worthwhile, but an incorrect physical model can conserve its own equations perfectly. The flow residual is particularly limited because flow is constructed to satisfy the same identity being checked.

**The simulation summary loses most of the budget history.**

It reports maximum residuals, not cumulative input, output, exchange, and storage change over the full run.

### What would make it substantially more impressive

#### First upgrade: a spatially resolved 1-D river model

Use river chainage—distance along the channel—and actual cross-section information.

A suitable governing structure is:

\[
\frac{\partial(AT)}{\partial t}
+
\frac{\partial(QT)}{\partial s}
=
\frac{\partial}{\partial s}
\left(A D_L\frac{\partial T}{\partial s}\right)
+
q_\ell T_\ell
+
\frac{bq_{\mathrm{net}}}{\rho c_p}
\]

Where:

- \(A\): wetted cross-sectional area.
- \(Q\): discharge.
- \(s\): distance along the river.
- \(D_L\): longitudinal dispersion.
- \(q_\ell\): lateral inflow per unit length.
- \(b\): exposed water-surface width.
- \(q_{\mathrm{net}}\): net surface heat flux.

Solve it with a conservative finite-volume method.

You do not need full 3-D CFD to make this excellent. A validated 1-D model plus a local 2-D mixing model near the outflow would be a much better investment.

#### Second upgrade: a defensible surface energy budget

Replace the single cooling coefficient with explicit radiation, sensible, and latent heat terms, using suitable meteorological forcing.

#### Third upgrade: genuine local plume transport

A depth-averaged advection–diffusion temperature field, constrained to the channel, would make a strong interactive overlay.

#### Fourth upgrade: analytical and observational validation

For the current one-reach model, an exact steady-state target is available:

\[
T^* =
\frac{Q_{\rm in}T_{\rm upstream}
+\sum Q_\ell T_\ell
+(V/\tau)T_{\rm air}}
{Q_{\rm out}+V/\tau}
\]

Use this for regression tests, alongside timestep refinement and observed temperature comparisons.

### In-world demonstration

At the bridge, the player changes upstream flow or hydrothermal discharge and watches:

- The warming signal propagate downstream.
- The plume spread.
- Cross-channel gradients develop.
- Fish habitat change after a physically meaningful delay.
- An instrument panel show heat input, atmospheric loss, and downstream export.

**This should be your flagship module.**

## `microclimate.py`

### Current level: coordinated environmental animation drivers, not really microclimate modeling

The sinusoidal temperature and wind functions are useful game approximations. They do not yet model local atmospheric conditions.

### Important limitations

- Daylight is always effectively a 12-hour sinusoid.
- Air temperature peaks at noon, whereas the daily maximum commonly lags solar noon.
- Season, latitude, terrain shading, elevation, and canopy are absent.
- Gusts are two repeating sinusoids, rather than a stochastic wind process.
- `steam_visibility()` is an artistic index.

The last distinction matters: **visible “steam” is condensed droplets, not water vapor itself**. Visibility depends on evaporation, mixing, cooling, humidity, and condensation—not just surface–air temperature difference.

There is also a concrete consistency issue in `build.py`: `air0` uses configured temperature parameters, but the weather trace is not passed those same temperature or humidity settings. The trace can therefore disagree with the configured starting weather.

### What would make it more impressive

- Solar position from location, date, and time.
- Terrain and canopy shading.
- Meteorological station forcing or defensible synthetic forcing.
- Relative humidity/dew-point calculations with ambient pressure.
- A correlated stochastic wind model, with a reproducible seed.
- Surface evaporation tied to vapor-pressure difference and aerodynamic transfer.
- A simplified heat–humidity mixing calculation to estimate condensation.

Use site pressure when modeling boiling or phase change rather than assuming sea-level conditions.

You can still render droplets with Godot particles. Their emission and disappearance should be driven by modeled conditions.

### In-world demonstration

The same hot pool looks different during:

- A cold humid morning.
- A dry windy afternoon.
- A sheltered versus exposed location.

The player can inspect evaporation flux and condensation potential rather than an unexplained visibility scalar.

## `pool_crust.py`

### Current level: procedural feature authoring, not a pool physics model

The recipes are useful for visual construction. But there is a significant mismatch between the claim of preserved outlines and the generated shell representation.

### Important issues

**The supplied polygon ring is not carried into the shell.**

The shell is reduced to a circle calculated from area:

```python
rw = sqrt(area / pi)
```

The original world polygon may remain untouched, but the generated water tests, aprons, and sections are circular approximations.

An equal-area circle is not guaranteed to contain an irregular mapped pool. Consequently, it is not automatically a safe exclusion geometry.

**The declared edge temperature is not actually attained at the water edge.**

At `r == r_water`:

\[
T = T_{\rm edge}
+ e^{-1.5}(T_{\rm center}-T_{\rm edge})
\]

Approximately 22% of the center–edge temperature difference remains.

**The cross-section renderer uses the default shelf multiplier.**

It does not pass the shell’s actual shelf ratio into `depth_at()`, so recipes such as Excelsior’s can be drawn inconsistently.

**Every pool receives the same radial color stops.**

You correctly disclaim a universal temperature–rainbow relationship, but the implementation still applies a universal radial palette.

**The whole-world mask resolution is too low for detailed exclusion work.**

A 256-pixel texture over 4,096 metres is roughly 16 metres per pixel. Some of the small pools are around one pixel across.

### What would make it more impressive

- Preserve the actual polygons.
- Use polygon buffers or signed-distance fields for margins and aprons.
- Separate submerged bathymetry from dry ground geometry.
- Constrain outflow routes using terrain elevation and drainage.
- Represent ground heat flux spatially rather than treating every apron as uniformly hot.
- Use local high-resolution tiles for pools and outflows.
- Attach uncertainty to inferred depths.

For color, separate:

1. Water absorption and scattering.
2. Water depth.
3. Bottom/substrate reflectance.
4. Microbial biomass and pigments.
5. Illumination and viewing conditions.

A simplified microbial growth model along outflow channels would be particularly relevant to Yellowstone and is currently missing.

### In-world demonstration

A pool inspection mode could reveal:

- The mapped outline.
- An explicitly labeled inferred cross-section.
- Water and substrate temperature.
- Microbial habitat bands.
- Which visual components are measured, modeled, or authored.

## `geochemistry.py`

### Current level: a useful geological rulebook, not geochemistry simulation

This module currently validates categories and palettes. It does not calculate fluid chemistry or mineral formation.

That is not a criticism of its usefulness—it is simply important to classify it correctly.

### Important issues

**Feature type alone cannot reliably determine a chemical system.**

`"fumarole"` appears in more than one system. `system_for_feature()` returns the first match, so an ambiguous feature is silently assigned to one category.

**Some descriptions are too categorical.**

“Acid-sulfate, low silica” is not a universal chemical definition. Likewise, “Mammoth terraces ONLY” should be understood as the project’s local scope, not a global geological rule.

**The palette guard is not comprehensively enforced.**

`forbid_whitening()` is not invoked in the supplied build path, and shell validation checks a substrate string rather than validating the entire material recipe.

Also, white color by itself is not evidence of travertine; siliceous deposits can be pale or white.

### What would make it scientifically substantial

A real geochemistry layer could model:

- pH and aqueous speciation.
- Dissolved silica.
- Calcium and carbonate chemistry where relevant.
- CO₂ degassing.
- Mixing and cooling.
- Mineral saturation.
- Precipitation/dissolution kinetics.

A central quantity is the saturation index:

\[
SI = \log_{10}\left(\frac{IAP}{K(T)}\right)
\]

But mineral selection, activity corrections, and database validity matter. For a sinter model, using quartz equilibrium indiscriminately would not substitute for appropriate amorphous-silica chemistry.

A tested geochemical engine such as PHREEQC, accessed from Python, is preferable to inventing a full speciation system. Its thermodynamic database and temperature range still need scrutiny.

Then connect modeled deposition to outflow velocity, chemistry, temperature, and available reactive surface area.

### In-world demonstration

Inspect an outflow and see:

- Fluid temperature and chemistry.
- Saturation state.
- Why deposition is favored in one location.
- A carefully labeled accelerated-time deposition replay.

This could become a distinctive showpiece, but it needs more research and input data than the present guardrail.

## `vegetation.py`

### Current level: simple biomass dynamics plus procedural placement proposals

The logistic-growth structure is a reasonable starting point. The placement system, however, does less than its description suggests.

### Important issues

**Planting proposals do not actually use the suitability evaluator.**

`propose_plantings()` does not evaluate local:

- Slope.
- Moisture.
- Canopy.
- Habitat suitability.

In the supplied build, it receives only the thermal exclusion function.

**Minimum separation is not enforced.**

A jittered grid does not guarantee the stated minimum separation. Neighboring candidates can be substantially closer than the grid spacing.

**The rendered suitability map is unrelated to the model.**

`guild` and `apron_mask` do not meaningfully affect the image. It is a radial demo pattern.

**Stable IDs and reproducibility need stronger guarantees.**

IDs can collide between proposal regions or seeds. Also, rejected candidates change how many random values are consumed, potentially changing later candidate positions.

A better design uses candidate-specific randomness derived from a stable namespace and candidate ID.

**The ecological quantities are normalized indices.**

That is acceptable for a game, but it limits scientific interpretation. A growth ledger in dimensionless units cannot be meaningfully balanced against kilograms of food consumed by bison.

### What would make it more impressive

- Actual raster or polygon environmental inputs.
- Species- or guild-specific response functions.
- Enforced spatial competition/separation.
- Biomass in physical units, such as dry mass per square metre.
- Soil-water storage with rainfall, evapotranspiration, drainage, and runoff.
- Seasonal growth and establishment.
- Disturbance history where justified by data.
- Explicit forage quality, not just bulk biomass.

Also distinguish **probability of establishment** from **spatial intensity in plants per area**. They are not interchangeable versions of \(\lambda\).

### In-world demonstration

A meadow responds to snowmelt, drying, and grazing, while an overlay explains whether growth is water-limited, season-limited, or forage-limited.

Keep planting proposals as reviewed authoring outputs. There is no need to make trees spontaneously regenerate during an ordinary walk.

## `insects_birds.py`

### Current level: one activity gate shared across ecologically different organisms

This is one of the most important modules to rethink scientifically.

### The main ecological problem

A flowering- and sunlight-dependent flying-insect index is not an adequate common food model for:

- Flower-visiting insects.
- Aquatic invertebrates eaten by dippers.
- A generalist raven.

Dipper food availability can depend strongly on aquatic larvae and benthic habitat, including food present when flying insects are inactive.

Ravens have a much broader diet and should not be reduced to this same resource signal.

### Other limitations

- The temperature response rises and then saturates; it does not decline under excessive heat.
- Resource depletion is not coupled to actual consumers in the supplied build: `consumed=0.0`.
- Resource abundance and activity are conflated.
- Bird timing is adjusted once, rather than continuously querying a changing resource.
- “More insects → longer foraging bout” is an assumption, not a general ecological law.

The comments about “no independent timers” overstate what the Python implementation demonstrates: it writes timer values into wildlife records.

### What would make it more impressive

Separate at least:

1. Terrestrial flying insects.
2. Aquatic benthic invertebrates.
3. Emergent aquatic adults.

Then consider:

- Temperature-dependent development.
- Water-temperature-driven emergence.
- Flood disturbance and habitat suitability.
- Resource abundance versus activity.
- Species-specific bird diets.
- Energy intake and foraging costs.

A Holling type-II functional response is a useful starting point:

\[
C(N)=\frac{aN}{1+ahN}
\]

It provides a defensible relationship between prey density and consumption, with search rate and handling time.

If you use stochastic behavior, use transition rates converted into timestep-consistent probabilities, rather than arbitrary per-frame chances.

### In-world demonstration

At the riverbank:

- Aquatic insects emerge as development conditions are met.
- Dippers forage where benthic prey and hydraulics are favorable.
- Strong wind suppresses adult flight without magically removing underwater prey.

That is a much stronger ecological explanation than a universal hover threshold.

## `fish.py`

### Current level: temperature-dependent animation tuning, not refuge selection

The function names and documentation imply more than the current implementation does.

### Important limitations

**No refuge is actually selected.**

`update_trout()` does not compare habitat alternatives or move fish toward a cold confluence. It preserves the existing route and adjusts hold time, speed, and lateral offset.

**The suitability score is calculated but not used for decisions.**

There is no habitat selection, route choice, or occupancy response based on `suitability_U`.

**Nearest reach by `z` is fragile.**

It can fail for curved or looping channels. Use river chainage or explicit reach membership.

**Hydraulic preference is oversimplified.**

Velocity is penalized monotonically, depth is represented by a fixed assumption, and the score mixes normalized quantities with dimensional quantities. This needs either units on the weights or explicit nondimensionalization.

Fish often have preferred velocity and depth ranges, not simply “less velocity is always better.”

**The pool check does not evaluate the actual fish route.**

It checks centerline vertices, not lateral offsets or the continuous segments between points.

**The refuge map is not a refuge map.**

Fish dots are assigned vertical positions using `hash(id)`, not habitat location. Python’s built-in string hash also makes those positions non-reproducible across ordinary separate processes.

### What would make it more impressive

- Explicit species and life-stage parameterization.
- Local depth, velocity, temperature, cover, and prey fields.
- Habitat suitability surfaces grounded in evidence.
- Exposure duration and acclimation, not only instantaneous temperature.
- Dissolved oxygen where relevant.
- Movement among accessible habitat patches.
- Costs of movement and competition.
- Actual refuge selection.

A bioenergetics model could compare food intake with metabolic and swimming costs. That is scientifically richer than another arbitrary weighted utility function.

Keep mortality out unless you have an adequately supported survival model. Behavioral refuge use is a valuable subject on its own.

### In-world demonstration

During a warming event, trout visibly relocate toward suitable cool habitat. A selected fish shows the trade-off between temperature, current, food, and cover.

## `grazers.py`

### Current level: sensible movement constraints plus biomass-based timing

The careful treatment of trophic-cascade claims is a strength.

But A* is a navigation algorithm, not an ecological movement model by itself.

### Important implementation issues

**Route checks only examine waypoints.**

A segment can cross a pool or apron even when both endpoints are outside.

**The planner allows diagonal corner-cutting.**

Diagonal moves are accepted without checking the two adjacent orthogonal cells or the full movement segment.

**Endpoints are not robustly validated.**

The start can be blocked, endpoint snapping can change validity, and replacing snapped endpoints with exact coordinates can introduce unchecked segments.

**The documentation does not match the algorithm.**

It says “4-connected, octile heuristic,” but the implementation uses eight neighbors and a Euclidean heuristic.

**The planner is not called by the build.**

So the current build does not demonstrate ecological rerouting.

**Grazer biomass interpretation is inconsistent.**

`graze_timing()` clamps biomass to `[0,1]`, while vegetation supports a separate capacity. It should distinguish absolute forage from fraction of capacity.

### What would make it more impressive

- Species-specific food preferences and intake.
- Forage quality and digestibility.
- Movement cost.
- Vigilance and rest budgets.
- Snow-depth effects.
- Group behavior.
- Habitat selection among accessible patches.
- Separate predation-risk scenarios with explicit uncertainty.

A resource-selection or step-selection model can inform movement costs. A* then solves feasible navigation between decisions.

### In-world demonstration

Bison shift meadow use as forage and snow conditions change, with a visible energy/forage budget—not merely longer grazing animations on a fixed loop.

## `snow_season.py`

### Current level: a legitimate approximation with several physical inconsistencies

A degree-day model is not inherently too basic. A calibrated degree-day snow model can be useful and credible.

The current implementation needs correction before adding sophistication.

### Important issues

**The named modifiers are applied to the wrong processes.**

Canopy interception and wind scour are described, but the modifiers only reduce melt.

For example, the meadow wind factor of `0.85` decreases melting; it does not remove or redistribute snow.

Likewise, a factor intended to represent greater north-facing retention should not increase melt.

**Thermal ground being “always bare” is too absolute.**

Snow persistence depends on snowfall intensity and ground energy flux. An apron is not automatically a uniformly snow-free surface.

**Existing thermal snow disappears without budget accounting.**

It is set to zero without recording melt, runoff, or the energy required.

**Rainfall is absent from soil recharge.**

Above the snow threshold, precipitation effectively disappears.

**Soil moisture has recharge but no losses.**

No evapotranspiration, drainage, or runoff is represented. Capping moisture also discards excess water without an accounting term.

**The ledger does not demonstrate actual storage conservation.**

It reports accumulation minus melt rather than verifying initial and final storage, including forced removals and rounding.

Summing millimetres across differently sized patches also does not produce a basin water volume.

**Phenology is globally uniform.**

All patches receive the same stage, and accumulated warmth eventually causes senescence regardless of species, photoperiod, frost, or drought.

### What would make it more impressive

First, fix the mass accounting and process definitions.

Then add:

- Rain/snow partitioning.
- Canopy interception.
- Variable snow density and compaction.
- Radiation and terrain effects.
- Ground heat flux.
- Soil-water storage.
- Drainage, runoff, and evapotranspiration.
- Species-specific phenology.

For high sophistication, use an energy-balance snow model. But a corrected and calibrated degree-day version should remain as a transparent comparison model.

### In-world demonstration

A winter-to-spring replay shows heterogeneous snow retreat, thermally influenced melt, soil recharge, and meadow green-up—with a water budget the player can inspect.

## `study_mode.py`

### Current level: a useful experiment configuration system, not yet an experimental science framework

This is a very good direction for the showpiece.

### Important issues

**Preset descriptions are stronger than the evidence.**

“Counterexamples prove…” should become “illustrate behavior within this model.”

“Air does not set river temperature” should be qualified: short-term response depends on residence time and forcing; air and surface exchange can matter strongly over longer periods.

**The hot-surge scenario is potentially confounded.**

It resets `hydro.attach` to `{}`, removing other configured tributary attachments. It also adds a fixed source rather than necessarily doubling the existing source.

**The allowed keys are broad string prefixes, not a strict scientific parameter schema.**

For example, the `clock_hour` prefix is not restricted to that exact key.

**There is no automated comparison of simulation outcomes.**

Configuration diffs are useful, but they do not quantify response, lag, exposure, or uncertainty.

### What would make it more impressive

- Exact intervention definitions.
- Automated A/B runs.
- Outcome metrics.
- Parameter sweeps.
- Sensitivity analysis.
- Uncertainty propagation.
- Calibration and held-out validation.
- Reproducible comparisons.

Useful outputs include:

- Thermal exposure duration.
- Suitable fish habitat area.
- Refuge occupancy.
- Insect emergence timing.
- Snow-water storage.
- Forage consumption.

Morris screening or Sobol analysis can be valuable, provided parameter ranges and correlations are scientifically defensible.

### In-world demonstration

A split-screen or replay comparison shows not just different scenery, but measured differences in temperature, habitat area, and behavior.

**This is the best place to make your Python work legible to viewers.**

## `build.py`

The orchestration is sensible, but several issues should be addressed before deeper coupling.

### Mixed scientific times

The river and vegetation advance for hundreds of seconds, while snow and moisture advance for days. Wildlife timing is then based on conditions before the seasonal update.

The final ecosystem can therefore combine states that do not represent the same instant.

**This is a major issue.** A coupled simulation needs a defined timeline and multirate update scheme.

### Incomplete build dependency coverage

The visible dependency dictionary hashes the ecosystem and configuration, but not `world.json` or `placements.json`, despite those affecting outputs.

Those files are mentioned in some sidecars, but that alone does not make the build identifier content-complete. I would also check how the unseen provenance implementation includes code revision.

### Fragile defaults

- `weather_frag["wind_xz_mps"]` can fail when that setting is omitted, despite an earlier default being used.
- `next(..., river_state[3])` evaluates the fallback index eagerly.
- Several pool, river, and patch IDs are hardcoded.
- Zero-duration simulations fail in the current river summary.
- Nonpositive timesteps and invalid physical inputs need explicit rejection.

### Architectural improvement

Split orchestration into:

- Input/schema validation.
- Scientific simulation.
- Visualization generation.
- Export.
- Validation.
- Publication.

The scientific engine should be callable without generating PNGs or parsing CLI arguments.

# 5. What scientific validation is missing

The unseen tests may cover some of this, but the supplied code does not establish it.

Your project needs more than bounds checks and conservation residuals.

## Numerical verification

- Analytical mixing tests.
- Steady-state reach tests.
- Timestep convergence.
- Spatial-grid convergence.
- Positivity and boundedness.
- Full-run heat and water budgets.
- Continuous-path collision tests.
- Reproducibility across separate processes.

## Physical validation

Compare predictions against relevant observations:

- Discharge.
- River temperatures.
- Meteorological forcing.
- Snow conditions.
- Habitat or behavioral observations where available.

Use held-out periods or locations, not only the data used to fit parameters.

## Ecological validation

Separate three questions:

1. Is the mathematical implementation correct?
2. Is the assumed mechanism plausible?
3. Does it predict actual observations adequately?

A correct implementation of an arbitrary activity curve only answers the first question.

## Honest uncertainty

Display uncertainty where the evidence supports it. Distinguish:

- Measurement error.
- Parameter uncertainty.
- Uncertain boundary forcing.
- Structural model limitations.
- Authored visual choices.

A more complicated model with unsupported coefficients is not necessarily more scientifically accurate.

# 6. Is additional research needed?

**Yes—but it should be targeted, and your existing research documents should be reviewed first.**

The biggest research needs are not more general Yellowstone facts. They are **process-specific parameters, observations, and evidence for model assumptions**.

Priority areas:

1. **Firehole hydraulics and thermal inputs**  
   Cross-sections, discharge, source flow/temperature, travel times, and temperature observations.

2. **Surface energy exchange**  
   Relevant meteorology, evaporation, radiation, and local pressure.

3. **Aquatic ecology**  
   Trout species/life stages, aquatic insect groups, dipper food relationships, and thermal refuge evidence.

4. **Hydrothermal chemistry and microbial mats**  
   Fluid chemistry, mineral phases, deposition mechanisms, and biologically defensible pigment/habitat relationships.

5. **Snow and soil water**  
   Precipitation, snow-water equivalent, terrain effects, soil storage, and thermal-ground heat flux.

For each modeled coefficient, record:

- What quantity it represents.
- Its units.
- Source or derivation.
- Applicable species/site/temperature range.
- Plausible uncertainty.
- Whether it is fitted, measured, transferred from literature, or authored.

Research documents can justify the model structure, but descriptive documents alone cannot calibrate numerical parameters.

## Bottom line

**The project is beyond a throwaway prototype in organization, but most of its scientific content is still basic.** The river model is the clearest exception: it is a legitimate numerical starting point, though still highly simplified and uncalibrated.

The strongest upgrade is not “put advanced equations into every file.” It is:

> **Build a coherent, validated scientific engine whose computed fields genuinely determine what the player sees and what the animals do.**

A conservative river solver, defensible heat budget, real refuge selection, aquatic resource dynamics, and an interactive experiment interface would make this a substantial Python showpiece—even without full CFD, a complete food web, or an elaborate underground geyser simulator.

The most useful next files to review would be your research documents, `baseline.yaml`, the validation/provenance modules, and the Godot ecosystem/wildlife scripts. Those would establish which gaps are genuine scientific omissions, which are integration issues, and which are already addressed elsewhere.
