## Cross-project issues
- Fixes-19 numbers run_hot_lowflow_with_tributaries_v2.py as the thermal-replay consumer, but the project already has aquatic_foodweb.compare_runs ingesting the modified pulse_doc; the doc does not say what cells layer compare_runs expects, so the "pocket vs solver cell" split needs an aquatic_foodweb contract check (yellowstone_python/aquatic_foodweb.py).
- Fixes-19 #15 asks channel_geometry to use --usgs-site to limit applicability, but the file was shipped without reading the flag at all; downstream river_world.py currently relies on cross_sections.json whose golden depths come from pure-DEM runs (test_channel_geometry.py:98 asserts 0.53/0.529/0.512/0.521/0.513), so adding a gauge-only override will fail that golden unless the test is also updated.
- Fixes-19 #11 bug is also present in tools/usgs_nwis.py:0360139e4f74 (same replace(tzinfo=UTC) misuse pattern); the doc does not reference usgs_nwis, so a tributary-only fix leaves the mainstem fetcher broken.

## Scientific validity flags
- q_out = q_in * 2.5 in run_hot_lowflow_with_tributaries_v2.py:187 violates mass conservation for every refuge cell added to the replay document, regardless of the fix doc.
- fetch_yellowstone_tributaries.py "documented_tributaries" list carries site_ids and stream names (07057925, 07054280, 07051500 etc.) with no verification that any of these gauges exist on NWIS or feed the Firehole; running the script against the real USGS API will log HTTP errors and silently use the authored temp/discharge in get_documented_temperature/get_documented_discharge.
- channel_geometry._dem_mean_depth derives depth from `water_y = pts[idx][1] + ...` which treats world.json centerline y as water-surface elevation; cross_sections.json ships with status "authored_estimate_from_usgs_3dep_dem" that the test asserts, overstating confidence in a DEM-only product.
- Hardcoded 11.5 C in every frame makes the tributary temperature a constant forcing that ignores diurnal and hot-day variation even for cells whose initial_c differs.
